01THE OPERATING PRINCIPLE

เลือก โหมด ก่อน
ค่อยเลือกโมเดล

งานที่ดีไม่ได้เริ่มจาก “รุ่นไหนเก่งสุด” แต่เริ่มจาก outcome, scope และความเสียหายที่ยอมรับได้

ทุ่มความฉลาดตรงที่พลาดแล้วเจ็บ — ประหยัดตรงที่พลาดแล้วแก้ง่าย

mode → model → leverage → proof
01ชัด + แก้ง่ายลงมือเร็ว
02หลายไฟล์ + เชื่อมกันวางแผนก่อน
03เงิน / auth / dataพิสูจน์ซ้ำ
02FOUR MODES / ONE DECISION

ให้โหมดบอก
วิธีคิดของงาน

ถ้ายังไม่รู้ว่าจะลงมืออย่างไร อย่าเพิ่งสั่ง Agent — เปลี่ยนเป็นโหมดที่ทำให้คำถามชัดขึ้นก่อน

01ASK

ส่องให้เห็นระบบ

อ่านอย่างเดียว สรุปเส้นทาง request, dependency และจุดที่ต้องแตะ โดยยังไม่แก้ไฟล์

“อ่าน @path แล้วสรุป
จุดที่เกี่ยวข้อง — ยังไม่แก้”
02PLAN

วางแผนก่อนเสี่ยง

แตกงานหลายไฟล์ ตัดสินใจ architecture และเขียน done criteria ก่อนอนุมัติให้ลงมือ

“เสนอ 2 แนวพร้อม
trade-off แล้วหยุดรอ”
03AGENT

ลงมือเป็นก้อนเล็ก

แก้ไฟล์ รันคำสั่ง และตรวจผลใน loop เดียว โดยรักษา scope ให้แคบพอจะ review ได้

“แก้เฉพาะ scope นี้
ห้าม refactor นอกนั้น”
04DEBUG

ตามหลักฐาน ไม่เดา

สร้างสมมติฐาน อ่าน log และ reproduce fail path ก่อนแตะโค้ด อย่าคลุมบั๊กด้วย try/catch

“reproduce → trace →
falsify → fix → verify”
03THE LOOP

ทำงานเป็นชั้น
ไม่ใช่ก้าวกระโดด

ทุกช่วงต้องทิ้งหลักฐานให้ช่วงถัดไป ลด context ที่ต้องจำ และทำให้หยุดได้โดยไม่เสียของ

  1. 01
    Define

    เขียน outcome, scope, constraints, invariants และวิธีตรวจ

    →
  2. 02
    Explore

    อ่านเส้นทางจริง เก็บ evidence และตรวจ assumption ก่อนแก้

    →
  3. 03
    Plan

    เลือกแนวทางที่พอดี พร้อม trade-off ที่กระทบงานจริง

    →
  4. 04
    Execute

    ลงมือเป็น diff เล็ก รัน test หลัง logical change

    →
  5. 05
    Verify

    รันสิ่งที่ล้มถ้างานผิด และเปิดดูของจริงเมื่อมี UI

    →
  6. 06
    Review

    ตรวจ diff รวม ความเสี่ยง และสิ่งที่ยังไม่ได้พิสูจน์

    ✓
